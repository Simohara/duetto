# 双声道连接、配对、音量误差测试与延迟校准：完整流程说明

适用版本：`rust-native`「合鸣 Duetto」（原 AirBridge-Rust；2026-11-02 WebView2 界面版：显式立体声对、测试目标、PIN 配对与重新配对、浅色/深色/跟随系统外观、输入电平表、导出诊断、按需导入旧版凭据、单实例；延迟精度 0.1 ms，PCM 电平修正，约 1 秒自动保存，地址变更迁移）。数据目录仍为 `%LOCALAPPDATA%\AirBridge-Rust`，EXE 仍为 `airbridge-rust.exe`。Python 版的差异见第 14 节。
本文所有行为、数值、提示文字均以源码为准，文件位置写在对应条目后面；没有在真实 HomePod 上验证过的内容单独标注为"未验证"。

---

## 0. 结论摘要

1. **双声道 = 两台音响各一条独立会话。** 左音响收到 `[L, L]`，右音响收到 `[R, R]`（`routing.rs` `Router::process`）。每台有自己的 RTSP 连接、硬件音量、延迟和电平修正。
2. **家庭 App 里组成"立体声对"的两台 HomePod，在本程序里也要组成立体声对（一个勾选框同时勾两台）。** 只连主节点时，主节点不会把另一个声道转发给从节点，Python 版和 Rust 版实测都只有主节点出声。OwnTone 对立体声对的做法也是给两台成员各建一个会话（owntone-server #1413）。以一对为例（地址和 ID 为示例值）：
   - `192.0.2.29` 客厅 (2)：立体声对**主节点**（TXT `flags` bit13 = 1）
   - `192.0.2.9` 客厅 (3)：立体声对**从节点**
   - 两台的 `tsid` 相同，例如 `B71C0F3E-0000-4000-8000-000000000000`

   两台还没在本程序里组对时，「音响」页顶部会提示一键组成；只连了其中一台时，开始桥接后状态栏也会提示（第 6 节）。
3. 发给每台的两个声道内容相同，所以**家庭 App 里谁被分配为左、谁为右不影响结果**，左右以本程序里的设置为准。
4. **"离得近的那台听起来像在独占"是声学上的优先效应**：两台放同样的内容时，人耳会把声音定位到**先到达**的那一侧，领先约 1 ms 就足以让声像几乎完全偏过去（1 ms ≈ 34 cm 声程）。离得近的那台通常也更响。所以校准要把延迟补到 0.1 ms，并且**只对麦克风所在的位置有效**（第 12 节）。
5. **音量校准不再改硬件音量**，而是在 PCM 里给较响的一台加"电平修正"（dB 衰减）。原因有两个：
   - HomePod 的硬件音量会被程序以外的因素改掉：触控、Siri、家庭 App，以及立体声对内部可能存在的音量联动。日志里实际记录到了音响上报的 `dvlc` 音量变化事件。
   - 旧方法依赖"音量每 1 % 等于 0.3 dB"的假设，这个假设没有验证过。
   电平修正是精确的 dB 值，音响改不了它；测试信号和正常播放走同一条路径，测到的就是你实际听到的差异。
6. 校准结果（延迟和电平修正）**立即生效并立即保存**。任何手动修改（延迟、电平修正、音量、声道、缓冲等）都会在约 1 秒后自动保存，不再只在关闭窗口时保存。

## 1. 工作原理

```
Windows 应用 ──输出到──▶ CABLE Input（VB-CABLE 虚拟声卡）
                                   │
                         CABLE Output（录音端）
                                   │  capture.rs：WASAPI 采集 → 线性插值重采样到 44.1 kHz
                                   ▼
                    multistream.rs：每 352 帧（约 7.98 ms）一个包
                                   │  连续测试时，calibration::Generator 替换为测试信号
                ┌──────────────────┴──────────────────┐
     Router（左路由，模式 1）               Router（右路由，模式 2）
     声道映射 → 总音量 × 测试增益 × 电平修正 → 延迟队列
                │                                     │
     有界队列 64 包（约 511 ms）             有界队列 64 包
                │                                     │
     会话：192.0.2.9:7000（LPCM、NTP、加密）       会话：192.0.2.29:7000
```

| 环节 | 具体行为 | 源码 |
|---|---|---|
| 声道模式 | 0 立体声 `[L,R]`；1 左声道 `[L,L]`；2 右声道 `[R,R]`；3 混合单声道 `[(L+R)/2]×2` | `routing.rs` |
| 硬件音量（独立音量） | 通过 `SET_PARAMETER volume` 发给音响：`-30 + 0.3 × 音量%` dB；0 % 发 -144 dB（静音）。音响端可能被其他因素改掉 | `main.rs` `drive_session` |
| 总音量 | **不发给音响**，按 `总音量/100` 的线性幅度比例缩放 PCM（50 % ≈ -6 dB），两台的相对差不变 | `gui.rs` `sync_gains` |
| 电平修正 | 每台一个 PCM 衰减值，−24 ～ 0 dB，精度 0.1 dB；正值和非法值一律按 0 dB 处理，**永远不会放大** | `routing.rs` `trim_db` |
| 共同起点 | 所有会话都完成 RECORD/FLUSH、采集预填 100 ms 之后，才发布同一个 NTP 起点，两台的 RTP 时间戳对应同一条时间线 | `playback_clock.rs` `SharedStart` |
| 同步包 | 每秒一次，告诉音响"此刻对应音频流的哪个位置"。按**两台共用的真实时钟**（共同起点之后经过的时间）计算，不用各会话的已发帧数。2026-11-02 实测：按已发帧数计算时，两台的发声时刻各自抖动 ±20～30 ms，相对延迟在 +26 和 −23 ms 之间来回跳，听起来就是拍频和声像漂移 | `playback_clock.rs` `frames_now` |
| 音响播放缓冲 | 「设置」页的 **播放缓冲** 滑块，300～2000 ms，步长 50 ms，默认 2000 ms（pyatv 是 1.5 秒），通过同步包告诉音响。上限 2000 ms 是流 SETUP 声明的 `latencyMax`，下限 300 ms 高于声明的 `latencyMin`（250 ms）。越大越能扛住 Wi-Fi 丢包，越小声音越及时、看视频时音画越同步。**下次开始桥接时生效**，两台总是使用同一个值 | `playback_clock.rs` `set_buffer_ms` |
| 采集时钟锁定 | VB-CABLE 用自己的时钟（实测比真实时间快约 729 ppm，每小时多约 2.6 秒）。采集重采样时用比例控制把输出锁定到真实时间：开始 5 秒后，每秒按"超前量相对基准的偏差 ÷ 20 秒"修正一次，最多 ±2000 ppm（音高变化 < 3.5 音分）。超前量会稳定在一个常数（729 ppm 时约 15 ms），不会持续增长撑满音响缓冲。仿真 10 分钟：不修正超前约 437 ms，修正后 < 30 ms | `capture.rs` `DriftControl` |
| 授时时钟 | 授时回复和同步包都使用"启动时读一次系统时间 + 之后用单调时钟累加"。Windows 自动对时会让系统时间突然跳几十毫秒，这样处理后不会影响播放中的会话 | `playback_clock.rs` `ntp_now` |
| UDP 发送拥塞 | 套接字发送缓冲满（Wi-Fi 拥塞）时，这个包按丢包处理，但仍留在重传队列里，音响可以请求重发；不会因此中断会话。本次桥接的丢包数显示在「音响」页输入电平旁（"丢包 N"，为 0 时不显示），每次开始时清零 | `main.rs` `sent_or_dropped` |
| 延迟 | 以微秒保存，换算为 `round(µs × 44100 / 10⁶)` 帧（每帧约 0.023 ms），上限 2000 ms。加大时在队列前端插入静音，减小时丢帧 | `routing.rs` `delay_us` |
| 全有或全无 | 任意一台连接失败或发送中断，**所有音响一起停止**；队列堵塞 250 ms 也一起停，绝不只剩一个声道 | `multistream.rs` |

"两台同时开始播放"由共同起点保证。剩下的时间差来自音响内部延迟和扬声器到聆听位置的距离，这部分由第 8 节的麦克风校准补偿。

## 2. 准备工作（逐项打勾）

### 2.1 Windows 侧
- [ ] 已安装 VB-CABLE。「音响」页"输入来源"下拉框里只会列出名称以 `CABLE` 开头且包含 `OUTPUT` 的录音设备；点"刷新"重新枚举时保留当前选择（已保存的设备暂时不在时，设置里仍记着它）。一个都没找到时，旁边出现 **下载 VB-CABLE ↗**，用浏览器打开 VB-Audio 官方页面（`https://vb-audio.com/Cable/`），安装后点"刷新"。
- [ ] CABLE Output 的默认格式必须是**立体声**，否则报"CABLE Output 必须提供立体声录音格式"。采样率任意，会被重采样。建议设为 44.1 kHz 或 48 kHz、2 声道（控制面板 → 声音 → 录制 → CABLE Output → 属性 → 高级）。
- [ ] 系统里不能有两个同名的录音设备，否则报"存在同名录音设备，请在 Windows 中重命名"。
- [ ] 要桥接的应用，输出设备设为 **CABLE Input**（点"打开音量混合器 ↗"；应用没出现在列表里时，先让它播放一下声音）。系统默认输出保持不变。

### 2.2 网络与音响
- [ ] 电脑和两台 HomePod 在同一局域网，组播（mDNS）不被路由器隔离。
- [ ] 建议在路由器里给两台 HomePod 做 DHCP 地址保留。新版扫描时会按 TXT `deviceid` 认出换了 IP 的音响，并迁移它的设置和配对（第 3.3 节），但地址固定仍然是最稳妥的。
- [ ] 家庭 App → 家庭设置 → 扬声器与电视 → 允许扬声器访问：选"同一网络中的任何人"等不需要家庭成员身份的选项，程序就可以直接用临时配对连接。如果连接时报"音响 … 验证失败，请检查配对或访问设置"，再按第 4 节配对。（各访问选项对第三方发送端的具体要求，本机未逐一验证。）
- [ ] 播放和校准期间**不要用 HomePod 触控、Siri 或家庭 App 改这两台的音量**，也不要让 iPhone、Mac 或同房间的 Apple TV（`192.0.2.59` 客厅 (4)）占用它们。音响被别的发送端占用时，日志里是 `receiver closed the control connection`；被外部改了音量时，日志里是 `音响 <IP> 事件 POST /command {value=dvlc volume=…}`。
- [ ] **Python 版 AirBridge 和合鸣 Duetto 不要同时运行**，否则会互相挤掉。合鸣 Duetto 自己只允许一个窗口：再次启动时弹出"合鸣 Duetto 已在运行，请切换到已打开的窗口。"并退出（第 2.4 节）。

### 2.3 校准用麦克风
- [ ] 用物理麦克风。名称以 `CABLE` 开头或包含 `LOOPBACK` 的设备会被拒绝。多声道麦克风只取第一个声道。
- [ ] **关闭自动增益、降噪和"音频增强"**：Windows 麦克风属性 → 高级/增强，以及麦克风自带软件（如 Yeti X 的 G HUB / Blue VO!CE）。
- [ ] 麦克风放在**你头部的实际位置**：两耳连线的中点、耳朵的高度、正对两台音响之间。**距离误差会直接变成延迟误差**：麦克风偏离 17 cm，就会差 0.5 ms，足以让声像偏向一侧（第 12 节）。不要把麦克风放在电脑旁边，那里不是你听的位置。
- [ ] 全心形指向的 Yeti X 请选"全指向"或"心形朝前"，正面朝向两台音响之间。
- [ ] 测量的约 20 秒内保持安静。

### 2.4 界面、外观与数据目录
- 界面由系统自带的 WebView2 显示，页面、动画库和字体都编译在 EXE 内。左侧栏是 **音响 / 校准 / 设置** 三页、运行状态（已停止 / 正在连接 / 正在播放 / 正在配对 / 正在播放测试音）、**总音量** 和 **开始桥接**（播放、连接、配对或测试音进行中变为 **停止**）。底部状态栏显示最近一条提示。
- 外观：「设置」页选 **浅色 / 深色 / 跟随系统**，左上角的太阳/月亮按钮也能切换；标题栏跟着变色，约 1 秒后自动保存。
- 单实例：启动时独占打开 `%LOCALAPPDATA%\AirBridge-Rust\instance.lock`；第二个实例弹窗提示后退出，并在诊断日志里记一条。文件打不开的其他情况（例如目录只读）不会阻止启动，只是不做单实例检查（`gui.rs` `run`）。
- 关闭窗口：窗口先隐藏，停止播放和配对，最多等 3 秒让会话发送 TEARDOWN，然后保存设置并退出（`gui.rs` `shutdown`）。
- 数据目录 `%LOCALAPPDATA%\AirBridge-Rust`（改名后没有变）：

| 文件 / 文件夹 | 内容 |
|---|---|
| `settings.json` | 普通设置（第 10 节"重启后"）。`settings.json.bak`：加载时修正过无效值时留下的原文件；`settings.json.bad`：无法解析时移开的原文件（第 11.7 节） |
| `<IP>.<端口>.dpapi` | 每台音响的配对凭据，当前 Windows 用户 DPAPI 加密 |
| `diagnostics.log`、`diagnostics.log.old` | 诊断日志，超过 1 MB 轮换一次 |
| `diagnostics-export\duetto-diagnostics.txt` | 「设置 → 导出诊断」生成的报告（第 13 节） |
| `last-failed-measurement.wav` | 最近一次测量失败时的麦克风录音（第 8.4 节） |
| `WebView2\` | 界面的浏览器数据。旧版放在 EXE 旁的 `airbridge-rust.exe.WebView2` 文件夹已不再使用，可以删除 |
| `instance.lock` | 单实例锁，内容为空 |

## 3. 第一步：扫描并认出两台音响

### 3.1 扫描
在「音响」页点右上角 **扫描音响**（扫描中显示"正在扫描…"）：程序浏览 5 秒 `_airplay._tcp`，每台音响一张卡片，显示名称和 `IP:端口`；同时记录 TXT 里的 `deviceid`（音响身份）、`tsid`（立体声对标识）和是否要求连接密码（`gui.rs` `scan`）。一台音响报告多个 IPv4 地址时只占一张卡片（第 3.3 节）。在本程序里组成立体声对的两台合并成一张"A + B 立体声对"卡片，排在最前（`app.js` `units`）。
名称后面的"(2)""(3)"是 mDNS 为避免重名自动加的后缀，不代表左右。扫描结果示例（地址为示例值）：

| 名称 | 地址 | 型号 | 说明 |
|---|---|---|---|
| 客厅 (2) | 192.0.2.29:7000 | AudioAccessory6,1 | 立体声对主节点 |
| 客厅 (3) | 192.0.2.9:7000 | AudioAccessory6,1 | 立体声对从节点 |
| 客厅 | 192.0.2.36:7000 | AudioAccessory5,1 | 另一台 HomePod mini，不属于这对 |
| 客厅 (4) | 192.0.2.59:7000 | AppleTV14,1 | Apple TV |
| 其他接收端 | 192.0.2.42:7000 | — | 其他 AirPlay 接收端 |

扫不到时，在页面底部"目标地址"里输入 IPv4 地址，点 **添加**（或回车）。不写端口按 7000，新卡片名为"手动添加"。手动添加的没有 `deviceid`，扫描到之后才会补上。

### 3.2 确认哪台物理音响对应哪个 IP
在第 7 步连续测试时听：**左路由播放 220 Hz 低音，右路由播放 330 Hz 较高的音**，每 4 秒两边同时出现一次"沙"的噪声脉冲（`calibration.rs` `Generator`）。如果和摆放位置相反，在立体声对卡片上点 **左右互换**。
**播放测试音** 只发给测试目标那**一台**：在卡片（立体声对里是对应的成员行）上点「测试目标」（按钮呈按下状态），或在底部"目标地址"里输入地址。前 2 秒左声道、后 2 秒右声道播 440 Hz，接着 2 秒静音，共 6 秒，**不经过声道设置**（`main.rs` `manual_test_tone`）。音量 = 该台的独立音量，PCM 再乘"总音量 × 测试音量"。播放中按钮不可用。它只用来检查单台能不能连上。单台 HomePod 可能播完整 4 秒，立体声对的成员可能只播属于自己的 2 秒，两种都算正常。

### 3.3 地址变更的自动迁移（新）
扫描到一台已知 `deviceid` 的音响出现在**新的 IP** 时（`gui.rs` `on_found`、`move_route`）：
- 它的勾选状态、声道、延迟、独立音量、电平修正都会移到新地址那一行。立体声对的搭档关系随地址一起更新；如果它是测试目标，目标地址也跟着更新。
- 它的配对凭据文件 `<IP>.<端口>.dpapi` 也会改名到新地址（`vault.rs` `swap`）。如果新地址原来也有凭据（两台音响互换了 IP），两个文件对调，中途失败会还原。
- 新地址原来如果已经有一行（例如另一台音响以前用过这个 IP），那一行会被换到旧地址；等它自己的音响被扫描到新地址时，再迁移一次。
- 状态栏提示"音响地址已从 A 更新为 B，设置与配对已保留"，并立即保存设置。凭据迁移失败时提示"配对凭据未能迁移"，设置仍然会迁移。
- **播放中不迁移**：只提示"「名称」的地址已变为 B，停止播放后重新扫描以更新"。因为当前会话还在使用旧地址。
- 一台音响报告多个 IPv4 地址时只用一个：优先本次扫描已用过的、已有该 `deviceid` 那一行的地址；同一次扫描里不会来回迁移。同一台音响在其他地址上的空白行（未校准、未配对、不在播放）会自动合并掉；有校准或配对的行保留，并提示"请只勾选一行"。播放中不合并。
- 旧版本保存的设置里没有 `deviceid`，第一次扫描时会按 IP 匹配并补上，之后的地址变化就能自动跟踪了。

## 4. 第二步：配对（只在需要时做）

**什么时候需要**：没有已保存的凭据时，程序默认先发 `/pair-pin-start`，再做临时配对（`main.rs` `send_audio_with_gain`）。只有连接报"验证失败"时才需要配对，验证失败**不会自动重试**（`multistream.rs` `authentication_failure`）。

**操作**：
1. 必须在**停止播放**的状态下进行（播放中 **PIN 配对** 按钮不可用）。
2. 在要配对的音响（立体声对里是对应的成员行）上点「测试目标」，按钮呈按下状态，底部"目标地址"同步为它的地址；也可以直接在"目标地址"输入 IP。配对目标看的是测试目标/目标地址，**不是勾选框**（`gui.rs` `pair_device` 使用 `self.host`）。
3. 点 **PIN 配对**，音响会播报或显示 4 位 PIN；状态栏提示"请在下方输入音响显示的 PIN。"，下方出现"音响显示的 PIN"输入框。配对进行中侧栏按钮变为"停止"，点它会取消配对（"已取消配对。"）。
4. 输入 **4 位数字**，点"提交 PIN"或回车。位数不对或含非数字时，状态栏提示"PIN 必须为四位数字。"，输入框清空，90 秒内可以重输。
5. **90 秒内**没提交，配对作废，提示"90 秒内未提交 PIN，已取消配对。"。其他失败提示"配对失败或超时，请检查 PIN 和音响访问设置。"。
6. 成功后，凭据用当前 Windows 用户的 DPAPI 加密，保存为 `%LOCALAPPDATA%\AirBridge-Rust\<IP>.<端口>.dpapi`，换用户或换电脑都无法解密。
7. 两台都需要时，分别配对。

**Corner cases**：
- **重新配对**：已有凭据的音响点 **PIN 配对** 时，底部先出现"已有配对凭据，确定重新配对？新配对成功前不会删除旧凭据。"，点 **重新配对** 才开始，点 **取消** 则不配对（"已取消重新配对，旧凭据未更改。"）。新凭据写入临时文件后才替换旧凭据（"重新配对完成，已替换旧凭据。"）；失败、超时或取消时提示末尾加"旧凭据未更改。"。换了目标地址、开始播放或停止时，确认会被收回。不再需要手动删除 `.dpapi` 文件。
- **凭据失效**：存在凭据但音响拒绝（`PairVerifyRefused` 或 401/403/470）时，报"验证失败"并停止，不会退回临时配对。处理方法同重新配对。
- **连接密码**：音响 TXT 里 `pw=true`，或 `sf`/`flags` 的 0x80 位为 1 时，卡片上显示"需要连接密码（暂不支持）"。本版不能发送连接密码；这类音响验证失败时，状态栏末尾追加"此音响开启了连接密码，当前版本暂不支持；可在家庭 App 调整访问设置。"（`gui.rs` `password_hint`）。这个标记不保存，重启后要重新扫描才显示。
- **IP 变化**：扫描时会随 `deviceid` 自动迁移凭据（3.3 节）。
- **导入旧 Python 版凭据**：「设置」页 **导入旧版配对凭据 → 导入**，只在点击时执行（`vault.rs` `import_python`）。只读取 `%LOCALAPPDATA%\AirBridge\credentials.dpapi.json`（超过 8 MB 拒绝，原文件不改），按已扫描音响的 `deviceid` 匹配，所以要先扫描；已有凭据的音响跳过，不覆盖。状态栏显示导入和跳过的台数；文件不存在、不是当前 Windows 用户创建的等情况只显示固定的原因，不显示文件内容。播放中不可用。导入的凭据能否通过真实 HomePod 的验证，未在实机确认；不能用时按重新配对处理。
- 命令行也可以配对：`airbridge-rust.exe --pair IP:7000`。已有凭据时命令行拒绝并提示到图形界面重新配对，不会覆盖。

## 5. 第三步：配置两条路由

**组成立体声对**：在一台卡片的声道里选 **左**（或 **右**），卡片下方会列出"选择另一台作为右（左）声道"的候选，点另一台即可；也可以点卡片上的 **组成立体声对**。家庭 App 里同 `tsid` 的两台在页面顶部有提示"「A」与「B」在家庭 App 中是一个立体声对，建议在这里也组成立体声对。"，点提示里的 **组成立体声对** 一步完成（提示中第一台为左）。组成后两台合并成一张卡片，固定一左一右；反了点 **左右互换**；点 **拆分**，或把其中一台改为立体声/单声道，会解除组对，两台回到立体声，延迟和电平修正保留（`gui.rs` `make_pair`、`unpair`、`set_route_mode`）。

| 项目 | 左成员 | 右成员 | 说明 |
|---|---|---|---|
| 勾选框 | ✔ | ✔ | 立体声对卡片上一个勾选框，同时勾选两台。**只勾这一个立体声对**，勾选状态只在点"开始桥接"时读取 |
| 声道 | 左 | 右 | 由立体声对固定。连续测试和校准**要求恰好一左一右**，否则报"请将两台音响分别设置为左声道和右声道" |
| 延迟 | 0.0 ms | 0.0 ms | 第一次校准前建议都设为 0，精度 0.1 ms。数字框输入后回车或移开焦点才生效 |
| 独立音量 | 例如 35 % | **同一个值** | 两台设成相同的值。立体声对可能联动音量，设成不同的值可能互相覆盖；左右平衡交给"电平修正" |
| 电平修正 | 0.0 dB | 0.0 dB | 校准自动写入。也可以手动调，−24 ～ 0 dB |

再在左侧栏设好 **总音量**；**断线自动重连** 在「设置」页，播放中不可改。

## 6. 第四步：开始桥接并确认两台都在发声

1. 点 **开始桥接**（`multistream.rs` `run`）：
   1. 每台音响一个线程：RTSP 连接 → 认证 → 会话 SETUP（NTP）→ 事件通道 → 流 SETUP（LPCM 44.1 kHz/16 位/立体声）→ `/feedback` → RECORD → FLUSH。
   2. **所有音响都就绪后**才开始采集，状态栏显示"2 台音响已连接，正在采集 CABLE Output。"，左侧状态变为"正在播放"。
   3. 采集预填 100 ms 后，发布共同起点，两台同时出声。
   4. 连接后"输入来源"旁出现输入电平表：CABLE Output 每包的峰值，−60 dB 及以下显示"无信号"，用来确认应用确实输出到了 CABLE Input（`multistream.rs` `peak_level`）。
2. **立体声对检查**，开始前在「音响」页顶部（`app.js` `renderNotices`）：
   - 家庭 App 同 `tsid` 的两台还没在本程序里组对：提示一键 **组成立体声对**（第 5 节）。
   - 勾选了一台设为左或右、但没有搭档的单台："「名称」只播放左（右）声道，另一半声音没有音响播放。"，带 **选择搭档** 和 **改回立体声** 两个按钮；卡片上也有同样的警告。
3. **立体声对检查**，连接后（`gui.rs` `stereo_pair_notice`），提示会附在"已连接"这条消息后面，不会阻止播放：
   - 某个家庭 App 立体声对只勾了一台："「名称」属于家庭 App 立体声对，只连一台时另一台不会发声：请两台都勾选，并分别设为左、右声道。"组成立体声对后两台总是一起勾选，所以这一条只会在两台还没在本程序里组对时出现。
   - 两台都勾了但独立音量不同："「A」与「B」是同一个立体声对，独立音量不同；立体声对可能联动音量，建议设为相同，用「电平修正」平衡。"
   - 这两类检查都依赖 `tsid`：扫描时读取，并保存在 `settings.json`（`home_pair`），重启后不用重扫；从没扫描到的音响（例如只手动添加过）不会提示。
4. **35 秒内**没有全部连上，所有连接都会取消。
5. 用第 7 步的连续测试确认**两台都在响**：220 Hz 和 330 Hz 都要听得到。

## 7. 第五步：开启连续测试（音量误差测试）

**前提条件**（`gui.rs` `toggle_test`）：
- 已连接，当前不在测量中，也不在 5 秒稳定期内。
- 本次会话**恰好 2 台**（"请选择恰好两台音响。"），一左一右。
- 两台的独立音量都大于 0（"两台音响的播放音量必须大于零。"）。

**点"开启连续测试"之后**：
1. 应用的声音被测试信号替换。
2. **两台使用相同的测试电平**：每台的测试增益都是 `测试音量 / 100`（`gui.rs` `test_gain`）。信号和平时播放一样，经过各自的硬件音量、电平修正和总音量。所以麦克风测到的就是**你平时实际听到的左右差异**，包括音响灵敏度、摆放距离、硬件音量是否被联动或被外部修改。（旧版是先在 PCM 里按 0.3 dB/% 抵消硬件音量差，现在不再这样做。）
3. 等待 **5 秒**，让队列和音响缓冲排空（"正在切换测试音，等待播放缓冲排空…"），然后显示"连续测试音已开启；两台使用相同测试电平。"
4. 测试信号：左声道 220 Hz、右声道 330 Hz，振幅约 −36 dBFS；每 4 秒同时出现一次 120 ms 的噪声脉冲，左右使用不同的随机种子。

**测试音量滑块**：测量时出现"麦克风削顶，请降低测试音量"就调小，"麦克风音量信号过弱"就调大。调整后重新进入 5 秒稳定期。
**总音量**为 0 % 时不能测量。

**测试期间**：
- 独立音量滑块不可拖动。
- 延迟和电平修正可以手动改，输入后回车或移开焦点生效；测量中和 5 秒稳定期内整页路由锁定（数字框、左右互换、拆分都不可用）。
- 不要改声道，也不要点 **左右互换** / **拆分**。

## 8. 第六步：测量并调平（延迟与电平）

### 8.1 操作
**开始桥接后至少等 30 秒。** 实测两台音响连接后约需 20 秒才同步到共用时间线上，未满 30 秒时程序会拒绝测量，并提示"刚连接，两台音响的同步还在稳定，请 N 秒后再测量"。断线重连后也要重新等待。

「校准」页顶部有三项检查：桥接已连接 / 一个立体声对，没有其他音响 / 已找到物理麦克风。连续测试中连接未满 30 秒时，进度条显示"同步稳定中 · 剩 N 秒"。

连续测试稳定后、测试音量 > 0 时，选好麦克风，点 **测量并调平**。状态栏显示"正在测量延迟和音量，约需 20 秒，请保持安静。"，进度条显示"正在测量延迟和音量，请保持安静 · 约 N 秒"。测量期间路由区、总音量、测试音量和麦克风下拉框都被锁定。

### 8.2 时间线（`calibration.rs` `measure`）
| 阶段 | 时长 | 播放内容 | 计算内容 |
|---|---|---|---|
| ① 切换 | 4 秒 | 切到错开脉冲信号，等发送队列和音响缓冲把旧信号播完 | — |
| ② 录音 | 13 秒 | 同一段噪声脉冲：左侧在每个 4 秒周期的第 0 秒，右侧在第 1 秒，两侧**不重叠**；脉冲之间保留 220/330 Hz 的低电平底音，流里不会出现长时间纯静音 | 延迟差和电平差，一次算出 |
| 结束 | — | 回到连续测试信号 | 生成修正值并立即应用 |

**为什么错开播放**（本版的改动）：旧版测延迟时两侧的脉冲同时播放，靠两种不同的噪声波形区分左右。一侧比另一侧响很多时（例如独立音量差很大，或者一台离得近），弱的那一侧会被强的那一侧淹没，每次都报"重复测试音不稳定或信号过弱"。错开之后，两侧不会互相干扰，单元测试里两侧相差 17 dB 也能正常测量。

### 8.3 配对规则（`calibration.rs` `analyze`）
- 用噪声的参考波形对录音做 FFT 互相关，取最多 12 个峰。峰要通过两道门槛：相关值不低于参考能量的 1 %，归一化相关度不低于 0.08。时间分辨率为 1 个采样（约 0.023 ms）。
- **按最先到达的直达声定位**：在每个最强峰之前 15 ms 内，取第一个达到最强峰一半的位置作为到达时刻。人耳定位依据的是最先到达的声音（优先效应），而在反射强的房间里，最强的相关峰可能是几毫秒之后的回声。2026-11-02 实测这个房间：按最强峰算两台基本对齐，按最先到达算右侧一直早约 10 ms。
- 录音里任何一个样本超过 32000（约 −0.2 dBFS）就报"麦克风削顶，请降低测试音量"。
- **配对**：对每个峰，在它后面 0.3～1.7 秒内找最接近 1 秒的峰，组成"（左, 右）"一对。下一个周期的左脉冲在右脉冲之后 2.3～3.7 秒，不会落进这个窗口，所以左右不会认错。左右两个峰都要在 4 秒后出现重复峰（偏差 ≤ 10 ms），这一对才算数。
- 每一对得到：延迟差 = `实际间隔 − 1 秒`；电平差 = `20·log10(右 RMS / 左 RMS)`。每个脉冲的 RMS 会先扣除它前面 150 ms（间隔 30 ms）里底音和底噪的能量，所以底音不会让电平算偏。任何一个 RMS 低于 30 就报"麦克风音量信号过弱，请提高测试音量"。

### 8.4 结果与一致性检查
- **延迟**：取所有配对的中位数。最大值与最小值相差超过 5 ms 时报"延迟测量不一致（相差 x ms），请保持安静、不要移动麦克风后重试"（反射会让单次定位偏几毫秒，所以门槛是 5 ms，结果取中位数）。可测范围 ±700 ms，由配对窗口决定。**结果为正 = 右侧更晚到。**
- **电平**：取中位数。相差超过 3 dB，或绝对值超过 18 dB，报"音量测量不稳定或差异过大"。**结果为正 = 右侧更响。**
- **一个有效配对都没有时**，按情况给出不同的提示：
  - "没有检测到测试脉冲：请提高测试音量或总音量，并确认选择了正确的麦克风"
  - "只检测到一侧的测试脉冲（N 个），另一侧太弱或没有发声；连续测试时请确认左侧 220 Hz 低音和右侧 330 Hz 高音都能听到"
  - "两侧测试脉冲没有稳定重复（检测到 N 个），请保持安静、关闭麦克风降噪后重试"
- **测量失败时**，13 秒的麦克风录音会保存到 `%LOCALAPPDATA%\AirBridge-Rust\last-failed-measurement.wav`（44.1 kHz 单声道，每次失败都会覆盖），报错末尾会附上路径，用来分析原因。录音只保存在本机。

### 8.5 修正值的生成（`calibration.rs` `propose`）
设测得的延迟差为 `d`（ms），电平差为 `s`（dB），当前延迟为 `dl`/`dr`，当前电平修正为 `tl`/`tr`：

- **延迟**：`dl' = dl + max(0, d)`，`dr' = dr + max(0, −d)`，然后两边同时减去较小的那个值，结果总有一边是 0 ms，**只给先到的一侧加延迟**。按 0.1 ms 取整。超过 2000 ms 报"所需延迟超出范围"。
  - 例：右边近、早到 0.46 ms → 右边延迟 0.5 ms，左边 0。
- **电平**：
  - `s > 0`（右更响）：`tr' = tr − s`。
  - `s ≤ 0`（左更响）：`tl' = tl + s`。
  - 然后两边同时减去较大的那个值，**保证较响的一台被衰减，另一台保持 0 dB，从不放大**。按 0.1 dB 取整。
  - 修正值在已有修正的基础上累加。例：原来左 −3 dB，测得右边又响 1 dB → 左 −2 dB、右 0 dB。
  - 任何一边需要低于 −24 dB 时报"所需电平修正超过 24 dB，请检查音响摆放或先调整独立音量"。
- 输入不是有限数值时报"测量结果无效"。
- 任一台的独立音量为 0（静音）时不能测量（"自动音量调平需要两台音响的播放音量都大于零。"）。

### 8.6 结果的应用（`gui.rs` 处理 `Event::Measured`）
- **延迟和电平修正都立即生效**，界面数值同步更新，**立即保存**到 `settings.json`。
- 状态栏："测得右侧比左侧晚 +x.xx ms、响 +y.y dB；已立即应用：延迟左 a、右 b ms，电平修正左 c、右 d dB。"
- 接着进入 **5 秒稳定期**（新的设置要经过发送队列和音响缓冲才会播出）。期间测量按钮不可用，结束后状态栏追加"已稳定，可再次测量验证。"
- 测量失败时显示"测量失败：<原因>。未应用结果。"，**一个值都不改**。
- 测量中断线、重连或停止时，结果被丢弃，不会套用到新连接上。
- **硬件音量在整个校准过程中都不会被改动。**
- 「校准」页结果区显示右侧相对左侧的到达差（晚/早 x.xx ms）和响度差（±y.y dB），以及左右两台当前的延迟和电平修正。声像图上方：|延迟差| ≤ 0.2 ms 且 |电平差| ≤ 0.5 dB 时显示"声像居中（已对齐）"，否则显示"已应用修正，请再次测量验证"（`app.js` `resultLabel`）。
- 结果只保存在本次运行的内存里，重启后不显示（修正值本身已保存）。开始新的桥接或测试音、断线重连、组对/拆分/左右互换，或手动改了延迟/电平修正后，结果清空为"—"，因为它已经不对应当前的设置（`gui.rs` `last_result`）。

## 9. 第七步：复测与验收

1. 等到"已稳定，可再次测量验证"，**直接再点一次"测量并调平"**。电平修正立即生效、测试信号走真实的播放路径，同一次测试里的复测就是有效的复测，不需要先结束测试。
2. **验收标准**（建议值）：复测显示 **|延迟差| ≤ 0.2 ms、|电平差| ≤ 0.5 dB**。达不到就再测一次，每次都在上一次的基础上继续修正。
3. 连续两次结果互相矛盾（例如延迟一会儿 +0.4、一会儿 −0.4）时，检查：麦克风自动增益、环境噪声、测量中有没有人移动，以及麦克风是否被碰动。
4. 点 **结束连续测试** 恢复应用声音（5 秒稳定期后显示"连续测试已结束，恢复应用声音。"）。
5. **断线重连或重新开始桥接后，建议再测一次**：AirPlay 接收端每个会话的内部延迟是否完全一致，未验证。如果重连后残差 > 0.5 ms，说明每次会话都不一样，每次开始都需要校准。

## 10. 日常使用

- **总音量**：在左侧栏，只按比例缩放 PCM，左右差不变。50 % 约 −6 dB，25 % 约 −12 dB。卡片上显示的电平"−xx.x dB"（独立音量或总音量为 0 时显示"静音"）= `-30 + 0.3 × 独立音量 + 电平修正 + 20·log10(总音量/100)`（其中 0.3 dB/% 只是显示用的估算）。
- **整体音量请用总音量，不要动独立音量**。改一台的独立音量会破坏左右平衡；立体声对的两台可能音量联动，单改一台可能两台一起变。
- **延迟、电平修正**：播放中可以手动修改，回车或移开焦点后立即生效，约 1 秒后自动保存。修改延迟的瞬间会有短暂的断音或跳音（插入静音或丢帧）。
- **播放缓冲**：在「设置」页，只能在停止时修改，下次开始桥接时生效。听音乐建议 1000～2000 ms；看视频想让音画更同步可以调小，但 Wi-Fi 不好时更容易跳音。
- **声道**：播放中切换立即生效；立体声对成员改为立体声或单声道会拆对。
- **外部改了音量**：播放中某台音响报告音量被触控、Siri 或家庭 App 改动时，状态栏提示"「名称」的音量在外部被修改……建议重新校准。"（每次连接每台最多一次）。程序不会改回去。
- **重启后**：独立音量、延迟、电平修正、声道、立体声对搭档、家庭 App 立体声对标识（`tsid`）、勾选状态、总音量、测试音量、麦克风、输入设备、自动重连、播放缓冲、外观都会恢复。已保存的输入设备或麦克风暂时不在时，选择框先显示别的设备，但设置里保留原名称，设备接回后点"刷新"会选回它。测试目标、连接密码标记和上次测量结果不保存。

## 11. Corner case 总表

### 11.1 发现与地址
| 情况 | 行为 / 处理 |
|---|---|
| 扫描不到 | 只看 `_airplay._tcp` 的 IPv4 地址，时长 5 秒；可以重扫或在"目标地址"输入后点"添加" |
| 同一台音响有多个 IPv4 地址 | 只用一个地址；其他地址上的空白行自动合并，有校准或配对的行保留并提示**只勾一行** |
| 音响 IP 变了，未在播放 | 按 `deviceid` 自动迁移设置和凭据（3.3） |
| 音响 IP 变了，正在播放 | 不迁移，提示停止后重新扫描 |
| 两台音响互换了 IP | 设置对调、凭据对调；文件对调中途失败会还原 |

| 手动添加 | 没有 `deviceid`，扫描到之后才能参与迁移。"添加"按 `IP:端口` 去重，只写 IP 等同 `IP:7000` |

## 12. 近处那台音响"独占"声像：原理与处理

**原理**：
- **优先效应**：同样的声音从两个方向先后到达时，大脑会把它定位在先到的方向。领先 0.5～1 ms，声像就明显偏向近处；超过约 1 ms，几乎完全偏过去，远处那台听起来像没在响。1 ms 对应约 34 cm 的声程差。
- **距离衰减**：近处那台还会更响，约为 `20·log10(远距离 / 近距离)` dB。例如 1.5 m 和 2.5 m，差约 4.4 dB。
- 两者叠加，就会出现"右边离我近，校准前只听到右边"。

**处理**：
1. 麦克风放在**头部的位置**（2.3 节），校准后**坐回麦克风所在的位置**听。声像只在这一点是准的：往一侧挪 17 cm，大约就差 0.5 ms，声像会跟着偏。
2. 按第 8～9 节测量、复测，直到 |延迟差| ≤ 0.2 ms、|电平差| ≤ 0.5 dB。正常情况下，结果是**近处那台被加延迟、并被衰减**。
3. **用耳朵验证声像居中**：
   1. 结束连续测试，播放一段人声为主的音乐。
   2. 在立体声对卡片上点 **拆分**：两台都变为"立体声"，播出完全相同的内容，延迟和电平修正保留。（需要单声道时再把两张卡片的声道改成"单声道"。）
   3. 坐在校准位置，人声应该出现在两台音响**正中间**。
   4. 偏向近处那台：给它的延迟每次加 0.1 ms，或者电平修正每次再降 0.5 dB，直到居中。偏向远处那台就反过来。
   5. 调好后重新组成立体声对：在原来左侧那台的声道里选 **左**，再点原来右侧那台，或用 **组成立体声对**。确认左右，反了点 **左右互换**。修改约 1 秒后自动保存。
4. 如果测量已经显示残差很小，但耳朵听仍然明显偏，说明麦克风的位置和你头部的位置不一致，重新摆放麦克风后再测。

**旧版本的问题**（已修正）：延迟只精确到 1 ms，最多会差 0.5 ms；音量通过硬件音量调整，可能被立体声对联动或外部操作抵消。这两点都会让校准后声像仍然偏向近处那台。

## 13. 故障排查：只有一台在响

按顺序排查：
1. **立体声对卡片勾选了吗？** 「音响」页顶部有提示时按提示处理（组成立体声对 / 选择搭档 / 改回立体声）；连接后状态栏的立体声对提示同样处理。
2. **声道是一左一右吗？**
3. **是不是近处那台独占了声像？** 见第 12 节。先用连续测试确认 220 Hz 和 330 Hz 都能听到。
4. **有其他设备占用吗？** iPhone 隔空播放、Apple TV 默认输出、另一台电脑上的合鸣 Duetto 或 Python AirBridge 实例。
5. **查日志** `%LOCALAPPDATA%\AirBridge-Rust\diagnostics.log`，会记录：
   - `音响 <IP> 事件 POST /command {type=… value=…}`：音响通过事件通道发来的消息，只记录类型和标量字段；`value=dvlc` 表示音响自己报告音量变了；
   - `控制连接中断（…，会话 N 秒）`：连接中断时，会话已经持续的秒数。
6. 连续测试时某台始终没声：记下 IP 和日志里对应时段的记录，再进一步排查。
7. **需要把日志发给别人时**，在「设置」页点 **导出诊断**：写入 `%LOCALAPPDATA%\AirBridge-Rust\diagnostics-export\duetto-diagnostics.txt`（每次覆盖上一份），并在资源管理器里选中它。文件里有程序版本、系统、WebView2 版本、运行状态、丢包数、输入设备和麦克风名称、去掉 `deviceid` 和 `tsid` 的设置、音响名称和 IP，然后是 `diagnostics.log.old` 和 `diagnostics.log`（各最多 2 MB，每行再过一遍脱敏）。不包含配对凭据、PIN、密码或音频。播放中也可以导出（`diagnostics.rs` `export`）。

## 14. Python 版的差异

Python 版没有随本次修改更新，仍是旧的校准方式。

| 项目 | Rust 版（本版） | Python 版 |
|---|---|---|
| 音响标识 | `IP:端口`，扫描时按 `deviceid` 迁移 | RAOP 设备 ID（MAC） |
| 凭据 | 每台一个 `<IP>.<端口>.dpapi`，随地址迁移；可在设置页按需导入 Python 版凭据（按 `deviceid` 匹配，不覆盖已有凭据） | `%LOCALAPPDATA%\AirBridge\credentials.dpapi.json` |
| 延迟精度 | 0.1 ms | 1 ms |
| 音量校准 | PCM 电平修正，测试信号走真实播放路径，不依赖音量曲线 | 改硬件音量，按 0.3 dB/% 预测，结束测试时生效 |
| 自动重连 | 连续失败 10 次才放弃，稳定播放 60 秒后清零 | 一直重试，间隔 `min(30, 2^n)` 秒 |
| 延迟测量 | 错开脉冲，一次录音同时算延迟和电平，重复偏差 ≤ 10 ms，范围 ±700 ms | 同时播放的两种噪声（11025 Hz 分析），重复偏差 ≤ 20 ms，另报相位和极性；一侧比另一侧响很多时可能被淹没 |
| 设置保存 | 任何修改约 1 秒后自动保存 | 关闭时，只保存勾选了的路由 |
| 播放缓冲 | 300～2000 ms 可调，默认 2000 ms | 固定 1.5 秒 |
| 采集时钟锁定 | 有 | 无 |
| 立体声对 | 显式组对（`settings.json` 的 `partner`），一起勾选，可左右互换、拆分；家庭 App 同 `tsid` 的两台提示一键组成；连接后仍检查漏勾和音量不同 | 无 |
| 连接密码 | 不支持；TXT 要求密码时显示标记，验证失败时提示原因 | 界面可以输入；按 pyatv 0.18 源码，只在 AirPlay 1 连接中使用，HomePod 走 AirPlay 2 时不会发送 |

两个版本的会话 SETUP、NTP 授时、LPCM 格式、同步包都相同（`pyatv_session.rs` 用 pyatv 0.18 的抓包做黄金测试）。

## 15. 已知限制与未验证项

1. **会话之间接收端延迟是否恒定，未验证**：见 9 第 5 点。
2. **立体声对的两台是否联动音量，未验证**：`dvlc` 事件是间接证据。本版的校准不依赖硬件音量，所以无论是否联动都有效。
3. **外部音量修改不会被自动纠正**：程序记录 `dvlc` 事件并在状态栏提示重新校准，不会把音量改回去，也不会自动重新校准。`dvlc` 事件的结构和其中 `volume` 的单位是按推测解析的（`event_pump.rs` `volume_change`），未在实机确认：如果不符，提示可能不出现，或者拖动音量后误报一次。
4. **只连主节点时频繁断连的原因未查清**：日志显示是音响主动正常关闭，按本文两台都勾选时不会走到这个场景。
5. **从节点长时间播放后偶尔断开**：日志里出现过反馈超时后连接被重置（间隔数小时），建议勾选自动重连。
6. **授时使用 NTP**：同步包已改为按共用的真实时钟报告，采集时钟也锁定到了真实时间。修复后实测 60 秒，两台的相对延迟稳定在 ±3～6 ms 以内，但没有做几小时的长时验证。
7. **实机未验证本版**：108 项单元测试（`cargo test --release --offline`，2026-11-02）覆盖延迟、电平修正、修正算法、旧设置兼容与修复、立体声对组对/拆分/互换、命令边界、状态快照、地址迁移与多地址选择、凭据迁移与中断恢复、旧版凭据匹配、外部音量事件解析、诊断导出、输入电平和丢包计数；WebView2 界面的完整操作流程和真实 HomePod 的校准效果还需要实机确认。
8. **重新配对已可在界面完成**：已有凭据时需先确认，成功后才替换旧凭据，不再需要手动删除凭据文件。对真实 HomePod 的重新配对，以及从 Python 版导入的凭据能否通过验证，都未在实机确认。
9. **本轮界面和启动改动没有启动 EXE 验证**：单实例锁、WebView2 数据目录、导航和命令来源限制（如果 WebView2 报告的页面地址不是 `http://duetto.localhost/…`，界面会无法工作）、关闭时的 3 秒等待、输入电平表、导出诊断后资源管理器选中文件，只经过单元测试和浏览器里的模拟后端（`web/mock.js`）检查。
10. **一台音响同时报告多个 IPv4 地址**的情况是按代码推断处理的，未在实机上见到过。
11. **连接密码**：只做了检测和提示，没有实现发送密码。
